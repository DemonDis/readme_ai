# Smart Diff Analysis

## Гибридный подход

При обновлении README.md расширение выбирает стратегию в зависимости от
размера diff'а кода. Замеряется длина `rawDiff` — если она в пределах лимита,
используется быстрый diff-only режим, иначе — полный repomix.

| Режим | Условие | Что получает AI |
|---|---|---|
| **Diff-only** | `rawDiff.length ≤ README_AI_DIFF_MAX_SIZE` | Старый README + отформатированный diff |
| **Repomix** | `rawDiff.length > README_AI_DIFF_MAX_SIZE` | Весь проект (XML), старый README вырезан |

### Зачем гибрид, а не всегда repomix?

Repomix делает полный слепок проекта — все файлы, все строки. Для мелких
изменений (добавили одну функцию, исправили баг) это избыточно:
- repomix работает 5–30 секунд на запуск
- отправка большого XML жрёт токены (деньги)
- AI видит кучу кода, не относящегося к изменениям, и может запутаться

Diff-only работает за миллисекунды, токенов почти не тратит, и AI фокусируется
именно на том, что изменилось. Если diff маленький — контекста достаточно.

Когда же изменений много, diff фрагментирован — AI не может понять структуру
проекта по обрывкам кода. Тут нужен repomix с полными файлами.

Порог намеренно консервативный (5000 символов). Можно настроить через
переменную окружения.

## Переменные окружения

| Variable | Default | Description |
|---|---|---|
| `README_AI_DIFF_MAX_SIZE` | `5000` | Максимальная длина сырого diff'а (символов) для diff-only. Больше — repomix |
| `README_AI_DIFF_TRUNCATE` | `8000` | Обрезать diff до N символов перед отправкой AI |

## Схема работы

```
                    ┌─────────────────┐

                    │  парсим hash    │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │  git diff <hash> │

                             │
                             ▼
              ┌──────────────┴──────────────┐
              │ rawDiff.length               │

              └──────┬───────────────┬───────┘
                     │               │
                     ▼               ▼
            ┌────────────────┐  ┌────────────────┐
            │ Diff-only      │  │ Repomix mode   │
            │                │  │                │
            │ README + diff  │  │ repomix        │
            │ → AI           │  │ (README filter)│

                     │          └────────┬───────┘
                     └───────┬───────────┘
                             ▼
                    ┌─────────────────┐
                    │ Пишем README.md │
                    │ + новый hash    │
                    └─────────────────┘
```

## Как работает git diff \<HASH\>

`git diff <HASH>` сравнивает **рабочую директорию (working tree)** с состоянием
на указанном коммите. Это **не** `..HEAD` — он не смотрит на коммиты, а просто
сравнивает файлы на диске (включая незакоммиченные правки) с тем, что было
в `<HASH>`.

### Пример с файлами

**Старт:** есть `calc.py` с функциями `add` и `mul`; хэш `d446c0c` — момент
последней генерации README.

**Проходит время:** пользователь добавил `sub`, `div` в `calc.py` и создал
`utils.py` с `validate_number`.

```
calc.py (было — 5 строк)          calc.py (стало — 13 строк)
┌─────────────────────┐           ┌─────────────────────────┐
│ def add(a, b):      │           │ def add(a, b):          │
│     return a + b    │           │     return a + b        │
│                     │           │                         │
│ def mul(a, b):      │           │ def sub(a, b):          │
│     return a * b    │           │     return a - b        │
└─────────────────────┘           │                         │
                                  │ def mul(a, b):          │
utils.py (не было)                │     return a * b        │
                                  │                         │
                                  │ def div(a, b):          │
                                  │     if b == 0:          │
                                  │         return None     │
                                  │     return a / b        │
                                  └─────────────────────────┘
```

#### 1. Без коммитов после хэша, без правок
```
git diff d446c0c
# → пусто. hash == HEAD, изменений нет.
```

#### 2. Есть незакоммиченные правки (до коммита)
```
git diff d446c0c
# → показывает изменения в calc.py (+sub, +div)
# → НЕ показывает utils.py (новый, untracked — не под git)

git diff --name-status d446c0c
# → M    calc.py
```

#### 3. После коммита
```
git diff d446c0c
# → показывает изменения calc.py И новый utils.py
# (теперь оба под версиями, diff видит всё)
```

### Что видит AI?

`git diff` показывает **только изменённые строки** (контекст ~3 строки),
но не полные файлы:

```diff
@@ -1,5 +1,13 @@
 def add(a, b):
     return a + b
 
+def sub(a, b):
+    return a - b
+
 def mul(a, b):
     return a * b
+
+def div(a, b):
+    if b == 0:
+        return None
+    return a / b
```

AI видит:
- строки, которые добавились или удалились
- несколько строк контекста вокруг

AI **не** видит:
- тело `add()` и `mul()` целиком
- содержимое новых файлов (`utils.py`) целиком
- связи между функциями
- структуру проекта

### Почему `git diff <HASH>`, а не `git diff <HASH>..HEAD`?

`git diff` с одним аргументом сравнивает **working tree vs коммит**.
С двумя аргументами (`..HEAD`) — **коммит vs коммит**. Это принципиально:

- `git diff <HASH>` — видит незакоммиченные правки (то, что на диске, но
  ещё не в коммите). Нужно для Force Update диалога.
- `git diff <HASH>..HEAD` — игнорирует незакоммиченные правки. Если изменить
  файл и не закоммитить, diff будет пустым — AI не увидит изменений.

Выбрали первый вариант, чтобы ловить все изменения, включая незакоммиченные.

## Вопросы и ответы

### Что если я создал новый файл, но не закоммитил?

`git diff <HASH>` **не покажет** untracked файлы — он работает только с теми,
что уже под git. Новый файл станет виден после `git add` или при коммите.

Это ограничение `git diff`. Решения:
- закоммитить новый файл (тогда diff его увидит)
- Force Update — тогда repomix найдёт файл на диске

### Что если коммиты плохие и по ним ничего не понятно?

Коммиты не используются. `git diff <HASH>` смотрит **только на содержимое
файлов на диске** — какие строки физически изменились. Сообщения коммитов
в diff не участвуют. Плохие коммиты не влияют на качество анализа.
